# 14 · 常见陷阱与排错清单

这一章不从零讲知识，而是把前面七章里那些"知道就绕开、不知道就卡半天"的地方集中列出来。

每一条都按 **症状 → 原因 → 怎么改** 组织。绝大多数问题不会抛异常，只会安静地给出错误结果——这才是化学信息学最麻烦的地方：**错误的代码往往能跑完，只是答案是错的。**

> 本章基于 RDKit 2025.09.x。不同版本的行为可能有差异，涉及版本的地方会注明。

---

## 一、数据读取与解析

### 14.1 不检查 `MolFromSmiles` 的返回值

**症状：** 脚本跑到一半突然报 `AttributeError: 'NoneType' object has no attribute 'GetNumAtoms'`，或者更糟——没有报错，但下游特征矩阵里少了一批分子，而且你没发现。

**原因：** `Chem.MolFromSmiles()` 遇到无法解析的 SMILES 时**不抛异常，返回 `None`**。这是 RDKit 里最容易踩的一个坑，因为解析失败的原因往往很隐蔽：手性标记写错、括号不配对、原子价态不合法。

**怎么改：** 把"返回 `None`"当作正常分支处理，而不是异常情况。

```python
from rdkit import Chem

def safe_mol(smiles):
    if not isinstance(smiles, str) or not smiles.strip():
        return None
    return Chem.MolFromSmiles(smiles.strip())

# 批量转换时，记录失败清单——不要静默丢弃
mols, failed = [], []
for smi in smiles_list:
    m = safe_mol(smi)
    if m is None:
        failed.append(smi)
    else:
        mols.append(m)

print(f"成功 {len(mols)} 个，失败 {len(failed)} 个")
if failed:
    print("失败样例：", failed[:10])
```

**为什么一定要打印失败清单：** 如果失败率是 0.1%，你会在一个小测试集上完全看不出来，等到跑全库时才发现特征矩阵少了几千行，而且已经不知道是哪些了。

### 14.2 SDF 文件里的坏记录会静默变成 `None`

**症状：** 用 `SDMolSupplier` 读一个有 1000 条记录的 SDF，结果只拿到 987 个分子，没有任何报错。

**原因：** SDF 是文本格式，任何一条记录的结构块损坏（原子数对不上、坐标缺失、编码异常），`SDMolSupplier` 都会把该条读成 `None` 而不是中断读取。

**怎么改：** 读取时显式过滤，并且**用 `SetDataField` 之前的顺序判断**——先确认分子对象有效，再取属性。

```python
supplier = Chem.SDMolSupplier("library.sdf")
mols = [m for m in supplier if m is not None]

missing = supplier.GetCounter() if hasattr(supplier, "GetCounter") else None
if len(mols) != len(supplier):
    print(f"注意：{len(supplier) - len(mols)} 条记录解析失败")
```

如果需要定位是哪几条坏了，逐条读并记录索引。**不要假设"没报错就是全部读进来了"。**

### 14.3 把 canonical SMILES 当作分子的唯一标识

**症状：** 用 canonical SMILES 去重，结果同一个化合物在库里出现了两次；或者反过来，两个不同的化合物被判定为同一个。

**原因：** canonical SMILES 只保证**同一套标准化流程下**、**同一个 RDKit 版本下**的确定性。它不处理这些情况：

- **立体化学**：`Chem.MolToSmiles(mol)` 默认保留立体信息，但如果你的分子对象在生成时丢了立体信息，输出就会退化
- **互变异构**：酮式和烯醇式是两条不同的 canonical SMILES，但化学上是同一物质
- **盐与游离态**：不做标准化的话，钠盐和游离酸是两条完全不同的字符串
- **版本差异**：不同 RDKit 版本的规范排序算法可能变化，跨版本比对可能失配

**怎么改：** 把 canonical SMILES 当成"标准化之后的结果"，而不是"原始数据的标识"。

```python
from rdkit import Chem

def canonical_key(mol):
    """用于去重的稳定键：去盐 + 中和 + 规范化，再取 canonical SMILES"""
    from rdkit.Chem.MolStandardize import rdMolStandardize
    mol = rdMolStandardize.FragmentParent(mol)     # 保留最大有机片段
    mol = rdMolStandardize.Uncharger().uncharge(mol)
    mol = rdMolStandardize.TautomerEnumerator().Canonicalize(mol)
    return Chem.MolToSmiles(mol)
```

配套的一点：**RDKit 的 `Mol` 对象不能直接当 `dict` 的键或放进 `set`**（它没有按值定义的哈希）。需要去重时用 canonical SMILES 字符串做键，或者用 `Chem.MolToSmiles` 的结果。

## 二、标准化

### 14.4 标准化之后忘记重建指纹

**症状：** 标准化流程写对了，但模型效果没变化。

**原因：** 标准化改变的是分子对象本身，而指纹是**在某个时刻**从分子对象算出来的。如果你在标准化之前就生成了指纹（或者把指纹缓存下来复用了），那么下游用的还是未标准化的版本。

**怎么改：** 严格按顺序：读入 → 标准化 → 去重 → **再**算指纹和描述符。

```python
# 正确顺序
mols = [Chem.MolFromSmiles(s) for s in smiles_list]
mols = [standardize(m) for m in mols if m is not None]
mols = dedupe_by_canonical(mols)          # ← 去重也在标准化之后
fps  = [generator.GetFingerprint(m) for m in mols]   # ← 最后才算指纹
```

第 13 章的完整 pipeline 就是按这个顺序组织的，可以对照检查。

### 14.5 盲目中和所有电荷

**症状：** 标准化的 `Uncharger` 跑完，季铵盐类化合物的正电荷消失了，或者化合物的整体电荷状态和你预期的不一样。

**原因：** 有些电荷是**永久电荷**，不是 pH 依赖的。季铵氮（如胆碱、许多抗菌药）在任何 pH 下都带正电，中和它等于改变了分子本身。

**怎么改：** RDKit 的 `Uncharger` 已经用基于 SMARTS 的规则处理了这一点，默认会保留季铵正电荷——**所以不要自己写"遍历所有原子把电荷清零"的逻辑**。如果你需要更严格的控制，用 `Uncharger(force=True)` 前先想清楚后果，并检查季铵类分子的处理结果。

另外一个容易被忽略的点：**中和策略本身有适用边界**（见 03 章的讨论）。如果下游任务对 pH 敏感——比如预测胃环境（pH 2）下的溶解度或吸收——把羧酸统一中和成中性形式会引入系统性偏差。通用 pipeline 默认"先中和"是合理的，但你需要知道这个假设什么时候不成立。

---

### 14.6 以为互变异构体标准化会给出"最稳定"形式

**症状：** 你期望标准化后得到化学上最稳定的互变异构体，实际得到的是另一个。

**原因：** 判断"哪个互变异构体最稳定"需要量子化学计算或实验数据，代价极高。`TautomerEnumerator` 做的是完全不同的一件事：**在同一个分子的一组互变异构体中，按一套确定的规则挑出一个"规范的"代表**。

它保证的是**一致性**（同一个分子永远映射到同一个代表），不是**物理正确性**（这个代表的能量最低）。

**怎么改：** 不要把标准化结果当作化学意义上的最稳定形式去解释。如果下游任务确实需要最稳定的互变异构体，那是另一个问题，需要专门的工具或计算。

反过来说，这也解释了一件事：**"两个分子是否相同"这个判断本身依赖于你选择的标准化规则**。换一套规则，去重结果就会变。所以标准化流程一旦定下来，要写进文档、固定下来。

## 三、指纹与描述符

### 14.7 新旧 API 混用

**症状：** 在一个文件里同时看到 `AllChem.GetMorganFingerprintAsBitVect(...)` 和 `rdFingerprintGenerator.GetMorganGenerator(...)`，两处生成的指纹对不上。

**原因：** RDKit 有一批老的指纹 API 至今仍可用，但已经不再推荐。**新旧 API 的默认参数不一定一致**（比如半径、位宽的默认值），所以在同一个项目里混用可能得到口径不同的指纹，而表面上看不出任何问题。

**怎么改：** 统一到新 API，全项目只用一套。

```python
from rdkit.Chem import rdFingerprintGenerator

# 新版（推荐）：生成器对象只建一次，复用
morgan_gen = rdFingerprintGenerator.GetMorganGenerator(radius=2, fpSize=2048)
fp = morgan_gen.GetFingerprint(mol)

# 旧版（了解即可，不要在新代码里用）
# from rdkit.Chem import AllChem
# fp = AllChem.GetMorganFingerprintAsBitVect(mol, 2, nBits=2048)
```

**顺便说一个性能点：** 生成器对象（`GetMorganGenerator` 的返回值）应该建一次就复用。在循环里反复创建生成器会带来不必要的开销。文档和教程里为了段落独立，常在每个片段里重新创建——照抄到生产代码里就不合适了。

### 14.8 默认 `fpSize` 带来的哈希碰撞

**症状：** 两个结构明显不同的分子，指纹相似度却高得离谱。

**原因：** 指纹是定长的位向量，多个不同的子结构片段可能被哈希到同一个 bit 上——这就是**碰撞**。位宽越小、分子越大，碰撞越严重。默认的 2048 位对中小分子通常够用，但**对于大分子库，1024 位的碰撞率可以超过 20%**。

**怎么改：** 按分子大小和库规模选位宽，并且心里有数：

| 场景 | 建议 |
|---|---|
| 中小分子、规模不大 | 2048 位（默认，通常够用） |
| 大分子（如天然产物、多肽） | 4096 位 |
| 需要精细区分相似分子 | 加大位宽，或改用计数型指纹 |

还有一个实用的调试手段：**`bit_info`**。它告诉你每个被置位的 bit 对应分子里的哪个原子环境，是排查"为什么这两个分子被判为相似"的唯一有效工具。

```python
from rdkit.Chem import rdFingerprintGenerator
from rdkit.Chem import rdMolDescriptors

gen = rdFingerprintGenerator.GetMorganGenerator(radius=2, fpSize=2048)
info = {}
fp = gen.GetFingerprint(mol, bitInfo=info)
# info 形如 {bit_id: [(atom_idx, radius), ...]}，可据此还原每个 bit 的化学含义
```

### 14.9 以为 MACCS 指纹的位宽可以调

**症状：** 想给 MACCS 指纹设置 `fpSize=4096`，发现参数不生效或直接报错。

**原因：** MACCS 指纹是**固定的 167 位**，每一位对应一条预定义的结构模式（"是否含有某类环"、"是否有某类原子"等）。它没有哈希过程，也就没有位宽的概念——位宽是它的定义的一部分，不可调。

**怎么改：** 接受这一点，把 MACCS 的定位摆正：它的价值在于**每位都有明确的化学含义、可解释性极强**，适合做特征筛选和结果解释；代价是信息容量小、区分力弱。**不要把它当作 Morgan 的替代品，它们是互补关系**（见 04 章的选择指南）。

## 四、子结构匹配与相似性

### 14.10 用 Python 循环做批量相似性计算

**症状：** 对一万个分子做相似性排序，脚本跑了几分钟。

**原因：** 逐个调用 `TanimotoSimilarity` 会反复跨越 Python 与 C++ 的边界，这部分开销远大于相似性计算本身。

**怎么改：** 用批量接口。它把整个列表一次性传进 C++ 层，能快出将近两个数量级。

```python
from rdkit import DataStructs

# 慢：Python 层循环
# sims = [DataStructs.TanimotoSimilarity(query_fp, fp) for fp in fps]

# 快：一次性批量计算
sims = DataStructs.BulkTanimotoSimilarity(query_fp, fps)
order = sorted(range(len(sims)), key=lambda i: sims[i], reverse=True)
```

`BulkDiceSimilarity`、`BulkCosineSimilarity` 等同理。

---

### 14.11 子结构匹配不加匹配数上限

**症状：** 在蛋白质或大分子上做子结构匹配，卡住不动了。

**原因：** 子结构匹配要找的是**所有**满足条件的原子映射组合。对于一个高频出现的简单模式（比如羧基）出现在一个大分子上，匹配数可能爆炸式增长。默认行为是找出全部匹配。

**怎么改：** 只关心"有没有"的时候，用 `HasSubstructMatch`；需要看匹配位置时，限制数量。

```python
# 只判断存在性——最快
has_carboxyl = mol.HasSubstructMatch(carboxyl_pattern)

# 需要位置信息，但限制数量
matches = mol.GetSubstructMatches(carboxyl_pattern, maxMatches=1000)

# 大分子上做模式筛查，建议同时设 useChirality=False（默认）并避开无约束的泛匹配
```

同理，**最大公共子结构（MCS）的计算复杂度更高**，`rdFMCS.FindMCS` 一定要设 `timeout`，否则可能长时间无响应：

```python
from rdkit.Chem import rdFMCS

res = rdFMCS.FindMCS(mols, timeout=30)   # 单位秒，务必设置
if res.canceled:
    print("MCS 计算超时，结果不完整")
```

### 14.12 把相似性阈值当成通用常数

**症状：** 照搬某篇文献的"相似性 > 0.7 算同一系列"，在自己的数据上效果很差。

**原因：** 相似性阈值**高度依赖三件事**：所用的指纹类型、分子的平均大小、以及任务目标。同一个 0.7 在 ECFP4 上和在 MACCS 上完全不是一个含义。

**怎么改：** 阈值要在自己的数据上标定，并且注意一个反直觉的事实：**对于虚拟筛选，Tanimoto 在 0.4–0.5 区间的"邻居"往往比 0.9 以上的更有价值**。原因在 07 章讲过——极高的相似度通常意味着同一系列的类似物，活性已知；中等相似度才可能是骨架跃迁。

所以不要盲目追求"找最像的"，先想清楚你的目标是**复用已知活性**还是**探索新结构类型**。

## 五、通用自查清单

在把任何化学信息学 pipeline 交给下游之前，逐条过一遍：

- [ ] 解析失败的分子有清单吗？失败率是多少？
- [ ] 标准化、去重、特征计算三步的顺序对吗？
- [ ] 全项目是否只用了**一套**指纹 API？
- [ ] `fpSize` 和分子大小匹配吗？有没有验证过碰撞程度？
- [ ] 相似性阈值是在**自己的数据**上标定的，还是照搬的？
- [ ] 批量操作有没有走 `Bulk*` 接口？
- [ ] MCS 和其他高复杂度计算设了 `timeout` 吗？
- [ ] 随机性来源（如构象生成、聚类）设了随机种子吗？
- [ ] 标准化规则写进文档了吗？（换一套规则，去重结果就会变）

最后一条最容易被跳过，但它决定你的结果**能不能被别人复现**——包括半年后的你自己。
